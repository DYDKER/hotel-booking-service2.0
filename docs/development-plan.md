# План разработки сервиса бронирования отелей

## Контекст проекта

Цель: написать простой HTTP JSON API для управления номерами отеля и бронированиями.

Выбранный подход:

- язык: Python;
- фреймворк: Django без Django REST Framework;
- БД: PostgreSQL;
- пакетный менеджер: Poetry;
- структура: src-layout;
- конфигурация: `.env` + `pydantic-settings`;
- тесты: pytest + pytest-django;
- линтеры: ruff + pre-commit;
- запуск: Docker + Docker Compose.

Ограничение обучения: основной код проекта пишется руками. Этот план не содержит готовую реализацию бизнес-логики, моделей или хендлеров.

Зафиксированные решения:

- URL оставляем как в ТЗ: `/rooms/create`, `/rooms/delete`, `/rooms/list`, `/bookings/create`, `/bookings/delete`, `/bookings/list`.
- Проверку пересечения броней делаем после базового CRUD.
- HTTP-порт сервиса: `9000`.
- Тексты ошибок API пишем на английском.
- Цену храним как `Decimal`, потому что это денежное значение.
- `date_end` считаем датой выезда: ночь на `date_end` не включается.
- Django migrations используем для разработки, дополнительно держим `schema.sql` для требования ТЗ.
- Добавляем `/health` для Docker healthcheck.

## План 1. Для технически подкованного человека

### 1. Зафиксировать стек и границы

- Использовать Django без DRF, потому что ТЗ разрешает любой фреймворк, а API маленький.
- Оставить URL-формат близко к ТЗ:
  - `POST /rooms/create`
  - `DELETE /rooms/delete`
  - `GET /rooms/list`
  - `POST /bookings/create`
  - `DELETE /bookings/delete`
  - `GET /bookings/list`
- Ошибки возвращать JSON-ом в формате `{"error": "..."}`.
- В README явно записать спорные решения: Django без DRF, URL-формат из ТЗ, формат ошибок, проверка пересечения броней.

### 2. Привести Poetry и Python к нормальному виду

- Проверить `pyproject.toml`.
- Исправить `requires-python`, если там стоит слишком новая версия вроде `>=3.14`.
- Целевой диапазон: Python 3.12 или 3.13.
- Добавить runtime-зависимости:
  - Django;
  - psycopg;
  - pydantic-settings;
  - gunicorn.
- Добавить dev-зависимости:
  - pytest;
  - pytest-django;
  - ruff;
  - pre-commit.

Проверка:

- `poetry --version`
- `poetry run python --version`
- `poetry show`

### 3. Подготовить структуру src-layout

Целевая структура:

```text
src/
  manage.py
  config/
    __init__.py
    settings.py
    urls.py
    wsgi.py
    asgi.py
  hotels/
    __init__.py
    apps.py
    models.py
    services.py
    views.py
    urls.py
tests/
docs/
```

Ответственность файлов:

- `config/settings.py`: настройки Django.
- `config/urls.py`: подключение URL приложения.
- `hotels/models.py`: таблицы `Room` и `Booking`.
- `hotels/services.py`: бизнес-логика и валидация.
- `hotels/views.py`: HTTP-хендлеры и JSON-ответы.
- `hotels/urls.py`: маршруты API.
- `tests/`: тесты API и бизнес-логики.

Проверка:

- Django видит приложение `hotels`.
- `manage.py check` проходит без ошибок.

### 4. Настроить конфигурацию

Создать `.env.example` с публичным шаблоном переменных:

- `SECRET_KEY`;
- `DEBUG`;
- `ALLOWED_HOSTS`;
- `POSTGRES_DB`;
- `POSTGRES_USER`;
- `POSTGRES_PASSWORD`;
- `POSTGRES_HOST`;
- `POSTGRES_PORT`.

Создать локальный `.env`, но не добавлять его в Git.

Подключить чтение `.env` через `pydantic-settings`.

Проверка:

- проект стартует с `.env`;
- при отсутствии обязательной переменной ошибка понятная;
- `.env` игнорируется;
- `.env.example` не игнорируется.

### 5. Настроить PostgreSQL

В `docker-compose.yml` описать сервис БД.

Требования:

- конкретная версия образа PostgreSQL, не `latest`;
- volume для сохранения данных;
- healthcheck;
- restart policy.

Создать `schema.sql` или `init.sql` с таблицами и индексами.

Минимальные таблицы:

- `rooms`;
- `bookings`.

Ключевые правила:

- `bookings.room_id` ссылается на `rooms.id`;
- при удалении номера удаляются брони;
- индексы на сортировку комнат и выборку броней.

Проверка:

- база поднимается через Docker Compose;
- данные не пропадают после перезапуска контейнера;
- Django может подключиться к БД.

### 6. Реализовать модели Django

Модель `Room`:

- текстовое описание;
- цена за ночь;
- дата добавления.

Модель `Booking`:

- ссылка на номер;
- дата начала;
- дата окончания;
- дата создания.

Проверка:

- Django check проходит;
- таблицы соответствуют смыслу ТЗ;
- удаление комнаты удаляет связанные брони.

### 7. Реализовать сервисный слой

В `services.py` вынести действия:

- создание номера;
- удаление номера;
- получение списка номеров с сортировкой;
- создание брони;
- удаление брони;
- получение броней номера;
- проверка валидности дат;
- опциональная проверка пересечения броней.

Сервисный слой должен возвращать данные или выбрасывать понятные доменные ошибки.

Проверка:

- view не содержит сложной бизнес-логики;
- ошибки не размазаны по всем хендлерам;
- сортировка ограничена разрешенными полями.

### 8. Реализовать HTTP-хендлеры

В `views.py` сделать хендлеры:

- `rooms/create`;
- `rooms/delete`;
- `rooms/list`;
- `bookings/create`;
- `bookings/delete`;
- `bookings/list`.

Требования:

- на успешный ответ возвращать JSON;
- на ошибку возвращать JSON с полем `error`;
- использовать корректные HTTP-статусы;
- не использовать `print`;
- не писать большой `try/except` в каждом хендлере без причины.

Проверка через curl:

- создание номера;
- список номеров;
- создание брони;
- список броней;
- удаление брони;
- удаление номера.

### 9. Добавить тесты

Минимальный набор тестов:

- создать номер;
- запретить номер с пустым описанием;
- запретить номер с невалидной ценой;

- запретить невалидную дату;

- получить брони номера, отсортированные по `date_start`;
- если делаешь усложнение: запретить пересекающиеся брони.

Проверка:

- `poetry run pytest`

### 10. Настроить ruff и pre-commit

### 11. Настроить Docker

## План 2. Для человека, который пишет первый проект

### Этап 0. Понять, что ты строишь

Ты делаешь не сайт с кнопками, а backend API.

Пользователь не открывает страницу в браузере. Он отправляет HTTP-запросы, например через curl, и получает JSON.

Проект должен уметь:

- добавить номер;
- удалить номер;
- показать номера;
- добавить бронь;
- удалить бронь;
- показать брони конкретного номера.

Главная мысль: сначала сделать маленький работающий путь, потом улучшать.

### Этап 1. Подготовить окружение

Что должно быть установлено:

- Python;
- Poetry;
- Docker Desktop;
- PyCharm;
- Git.

Проверяешь команды:

```text
python --version
poetry --version
docker --version
```

Если команда не находится, не идешь дальше. Сначала исправляешь установку.

### Этап 2. Навести порядок в корне проекта

В корне проекта должны быть:

```text
README.md
pyproject.toml
poetry.lock
.gitignore
```

Потом появятся:

```text
.env.example
Dockerfile
docker-compose.yml
schema.sql
src/
tests/
docs/
```

Не должно быть:

```text
djvenv/
venv/
.env в Git
```

Важно: `.venv/` может быть в папке проекта, но она должна быть в `.gitignore`.

### Этап 3. Поставить зависимости

Через Poetry ставишь только нужные библиотеки.

Основные:

- pytest;

После установки проверяешь:

```text

```

Если зависимости видны, этап готов.

Нужно получить структуру:

```text

  manage.py
```

Что значит каждая папка:

- `src/` - место, где лежит код приложения;

- `hotels/` - твоя предметная область: номера и брони.

На этом этапе не пишешь API. Только создаешь каркас.

Проверка:

```text

```

Django должен знать, что приложение `hotels` существует.

Идея:

- создать app;
- добавить app в настройки;
- подключить URL приложения к главным URL проекта.

Проверка:

- Django стартует;
- ошибок про неизвестное приложение нет.

### Этап 6. Сделать настройки через `.env`

Зачем:

- секреты нельзя хранить в коде;
- настройки отличаются на локальной машине и в Docker;
- ревьюер должен видеть шаблон, но не твои пароли.

Файлы:

```text

```

```text

```

```text

```

Проверка:

- если `.env` есть, настройки читаются.

Сначала поднимаешь БД через Docker Compose.

Потом настраиваешь Django, чтобы он подключался к PostgreSQL.

Важно:

- не использовать SQLite как основную БД;
- не использовать `postgres:latest`;
- данные должны сохраняться между перезапусками;
- у БД должен быть volume.

Проверка:

- контейнер БД запущен;
- Django может подключиться;
- после перезапуска данные не исчезают.

Нужны две модели:

```text
Room

```

`Room` отвечает за номер отеля:

- описание;
- цена;
- дата добавления.

`Booking` отвечает за бронь:

- какой номер;

Проверка:

- можно создать таблицы;

### Этап 9. Сделать бизнес-логику отдельно

Не пиши всю логику во view.

Разделение:

```text

services.py  решает, что делать

```

Пример мысли:

```text

service удалил номер
view вернул JSON
```

Так код легче тестировать и читать.

### Этап 10. Сделать API номеров

Сначала реализуй только номера.

Порядок:

2. Получить список номеров.
3. Добавить сортировку.
4. Удалить номер.

После каждого пункта проверяй curl-запросом.

Не переходи к броням, пока номера не работают.

### Этап 11. Сделать API броней

Порядок:

1. Создать бронь для существующего номера.
2. Запретить бронь для несуществующего номера.
3. Проверить формат дат.
4. Запретить дату окончания раньше или равную дате начала.
5. Получить список броней номера.
6. Удалить бронь.

Проверка:

- бронь создается;
- бронь видна в списке;
- список отсортирован по дате начала;
- удаление работает.

### Этап 12. Добавить проверку пересечения броней

Это дополнительное усложнение, но оно даст плюс.

- нельзя создать бронь с 18 по 21 июня;
